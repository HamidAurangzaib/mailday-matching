1. Executive Summary

MailDay Matching is the internal admin web app your team uses every day to manage pen-pal matching, members, donations, influencer partnerships, and monthly pack delivery. It connects to Shopify, ReCharge, Klaviyo, Slack, and Anthropic (the AI that suggests matches), and stores all of its information in a database called Supabase.

Bottom line: the app is well-built and the team has clearly invested in structure and clarity. It is also a one-person admin tool that has quietly grown into a system holding real customer and children's information — and several of the doors and locks have not kept pace with that growth. None of the issues below are catastrophic on their own, but a few of them should be fixed within the next week, and a few more before the business doubles in size.

What does each level mean?

  • Critical A real attacker (or a curious customer) could realistically cause damage today. Fix this week.
  • Important A weakness that is unlikely to be exploited tomorrow, but will hurt as you grow. Fix this month.
  • Improvement A clear best-practice gap. Not urgent; bake into the next sprint or two.
  • Nice-to-have Polish, future-proofing, or convenience. Plan for the next quarter.

The three things we recommend fixing first

DO THIS WEEK · #1 Make webhook secrets mandatory. Right now, if the "secret password" for our Shopify, ReCharge, or Klaviyo connections is not configured, the server still accepts incoming messages and acts on them. That is the online equivalent of a delivery door that opens regardless of whether the courier shows ID. A bored attacker who guesses the URL can create fake parent accounts, log fake donations, or end real matches. (See section 3.2)
DO THIS WEEK · #2 Stop trusting the email field on public forms. Three public pages — Enroll, Give-a-Key PO-Box, and the affiliate tracker — accept an email address and then change records associated with that email, with no proof the person sending the form actually owns it. The most direct consequence: anyone who knows a customer's email can change their mailing address. (See sections 3.3 and 3.5)
DO THIS WEEK · #3 Stop storing the admin login key in a place every script on the page can read. The token that proves you are logged in is stored in the browser's "localStorage", which any piece of JavaScript that runs on the page can read. If a third-party widget were ever added — or a single cross-site scripting bug crept in — a 30-day admin login could be stolen silently. (See section 3.1)

What we did NOT find

  • No evidence the database has been tampered with.
  • No SQL injection vulnerabilities in the code we reviewed.
  • No passwords stored in plain text (they are properly hashed).
  • No obvious exposed API keys in the public-facing frontend code.

2. What's Working Well

Before the gaps, the wins. A lot of the foundation is correct, and that matters because most of the fixes below are small additions on top of a solid base — not rewrites.

✓ DONE RIGHT Passwords are stored securely. Even if someone walked out of the office with the entire database, they would not see anyone's actual password — only a one-way scramble of it (called a "bcrypt hash"). This is the industry standard and the code uses it correctly.
✓ DONE RIGHT Two roles are clearly separated. There are two kinds of users: Admin and VA (virtual assistant). The code consistently hides sensitive fields like mailing addresses, internal notes, and safety flags from the VA role. That layered approach is exactly what you want.
✓ DONE RIGHT The code is well organised. Every feature lives in its own file, the database queries are parameterised (which blocks a whole class of attacks called "SQL injection"), and the project uses industry-standard tools (TypeScript, React, Express, Supabase, Tailwind). A new developer joining the team would be productive within a week.
✓ DONE RIGHT Incoming webhook signatures CAN be checked. The code knows how to verify that a message from Shopify is really from Shopify (and same for ReCharge and Klaviyo). The mechanism exists — the only problem is that it can be disabled by forgetting to set one environment variable. See section 3.2 for how to make it mandatory.
✓ DONE RIGHT Logs do not show sensitive data. The logging tool (pino) is configured to hide login keys and session cookies from log files. If logs are ever shared with a vendor for debugging, they will not contain those secrets.
✓ DONE RIGHT The user interface is consistent and accessible. The team picked a high-quality component library (shadcn/Radix) so things like dialogs, dropdowns, and keyboard navigation work the way users expect. The mobile layout works. Icons have labels for screen readers.

3. Critical Issues — Fix This Week

These are issues where a motivated person could cause real damage today, with skills that are freely taught online. We strongly recommend addressing all five within the next week.

Critical

3.1 Login key stored where any guest script can grab it

Effort: Medium
What it is
When you sign in, the app puts your 30-day login key into a part of the browser called localStorage. Anything else loaded on the page — a tracking script, an ad-blocker extension, a future copy-paste of code from a tutorial — can read it.
Analogy
Imagine the office key is left in the top drawer of every reception desk in every coffee shop you visit, "just in case you forget yours". You probably will never have a problem. But the day someone you don't know sits at that desk, your office is open to them for the next 30 days.
What an attacker could do
Steal your login key once and use it for a month. They would not need your password. They could read every parent, child, and donation record, and approve or reject Give-a-Key applications.
What to fix
Move the login key into an HttpOnly cookie (a special kind of cookie that browser scripts cannot read), and turn on a security feature called Content Security Policy (CSP) that the code currently has switched off.
Effort
Roughly 1–2 developer days. The login flow has to be moved from "send me a token" to "set me a cookie", and the CSP rules need to be tuned for the third-party fonts the app uses.
For the dev team: auth context lives in artifacts/mailday/src/lib/auth.tsx; CSP is disabled in artifacts/api-server/src/app.ts. Add cookie-based auth, set SameSite=Lax; Secure; HttpOnly, and re-enable helmet's CSP with a whitelist for Google Fonts.
Critical

3.2 Outside delivery doors will open without checking ID

Effort: Small
What it is
When Shopify, ReCharge, or Klaviyo send us a message (called a "webhook"), the code is supposed to check a secret password that proves the message is genuine. If that secret is not configured, the code currently logs a warning and accepts the message anyway.
Analogy
It's a back door at the warehouse with a card reader. If the card reader is unplugged, the door is supposed to stay locked. Right now it stays open.
What an attacker could do
If even one of the three secrets is missing, anyone on the internet who guesses the webhook URL can: create fake parent accounts, log fake donations to the Give-a-Key fund, mark real subscriptions as cancelled (which ends matches and triggers rematch emails), or fake "I opened your email" events to skew metrics.
What to fix
Make the secret required — if it is missing, the webhook endpoint should refuse all messages with a 503 error and the operator should be paged. The change is a one-line condition in three files.
Effort
Half a day, including checking the three production secrets are set.
For the dev team: see artifacts/api-server/src/routes/webhooks.ts lines 47–55 (Shopify), 148–156 (ReCharge), and 393–401 (Klaviyo). The pattern if (secret) { …verify… } else { warn } should become if (!secret) return 503; …verify….
Critical

3.3 Anyone can change a customer's shipping address

Effort: Medium
What it is
The public "Enroll my children" form (/enroll) and the Give-a-Key PO-Box form ask for an email address, look up the matching customer in the database, and then overwrite that customer's mailing address with whatever was typed into the form. There is no proof the person filling out the form is the actual customer.
Analogy
It's like the front desk of an apartment building updating your forwarding address because someone in line said "I'm Jane, and Jane's new address is '123 Other Street'." No ID is checked.
What an attacker could do
Knowing only a customer's email (often guessable or scraped from social media), an attacker could redirect that customer's monthly pen-pal letters — and any other mail — to an address of their choosing. For a children's product, this is a particularly serious safety concern.
What to fix
Send the customer a one-time confirmation link by email and only apply the address change after they click it. The same mechanism the password-reset flow already uses can be re-used.
Effort
1–2 developer days. The email-sending infrastructure already exists (Resend is wired up for password reset).
For the dev team: artifacts/api-server/src/routes/enroll.ts and artifacts/api-server/src/routes/give-a-key.ts (the /give-a-key/po-box handler). Re-use the reset_token pattern from auth.ts.
Critical

3.4 Receipt upload accepts any file from anyone

Effort: Small
What it is
When a Give-a-Key recipient uploads a photo of their PO-Box receipt, the server: (a) accepts any file type by trusting the filename's extension; (b) does not check the file size; (c) overwrites any earlier file with the same name; and (d) saves it to a publicly readable folder, meaning the resulting URL works for anyone on the internet who guesses it.
Analogy
It's a donation drop-box on a public street that accepts anything you put in it, no size limit, and the contents can be viewed by anyone walking by.
What an attacker could do
Upload very large files to run up your Supabase storage bill; upload disguised malware files to a URL that looks like it belongs to MailDay; or simply view other families' receipts (which may include names, addresses, and partial payment info).
What to fix
Three small changes: (1) check the file's real type by reading its first few bytes, not just the filename; (2) reject anything over (say) 5 MB; (3) put the receipts in a private Supabase bucket and generate short-lived links when an admin needs to view one.
Effort
1 developer day plus a short Supabase storage settings change.
For the dev team: artifacts/api-server/src/routes/give-a-key.ts lines 166–187. Use a magic-byte sniffer (e.g. file-type npm package), cap fileBuffer.length, set the bucket to private, and replace getPublicUrl with createSignedUrl (60-min expiry).
Critical

3.5 Influencer commissions can be inflated by anyone

Effort: Small
What it is
There is a public URL that increments an influencer's "conversion" count and the commission they are owed. It accepts any affiliate code from any caller, and it also accepts a "parent ID" that tags a real customer to that influencer — again, with no proof.
Analogy
A tip jar that anyone can drop slips into, each slip reading "credit this barista $14 for serving me", with no check that the customer was ever served — and the slips are tallied automatically against payroll.
What an attacker could do
Inflate a friendly influencer's payout, sabotage a competitor's commission records, or attach real customers to the wrong influencer to skew growth metrics.
What to fix
Only the Shopify checkout (which we trust) should be allowed to record a conversion. Require an HMAC signature on this endpoint or move the conversion-recording logic entirely into the Shopify-orders webhook.
Effort
Half a day.
For the dev team: artifacts/api-server/src/routes/influencers.ts lines 250–271. Either add HMAC verification (shared secret with the calling Shopify script), or move the conversions++ logic into webhooks.ts's Shopify-order handler using the existing X-Shopify-Hmac-Sha256 check, and delete the public route.

4. Important Issues — Fix This Month

These do not need to be fixed this week, but each is a real exposure that will start to bite as the business grows or as more people are given accounts.

Important

4.1 Login key lasts 30 days and cannot be cancelled

Effort: Medium
Plain English
Once you sign in, the key is valid for 30 days, and there is no "log everyone out" button. The current "Log out" button just deletes your local copy — it doesn't tell the server to invalidate the key. If you lose a laptop, that laptop can still log in for up to 30 days.
Fix
Shorter access keys (15 minutes), longer refresh keys (1–7 days), and a server-side "revoked tokens" list. Or move to a session library that already does this.
Effort
2–3 days.
Important

4.2 Rate limiting only on the login screen

Effort: Small
Plain English
You can only try to log in 20 times in 15 minutes per network address, which is good. But the "Forgot password" and "Change password" forms have no such limit, and the public forms (enroll, GAK apply, GAK PO-box) can be submitted as fast as someone can type. Anyone could send 10,000 password-reset requests in a minute to flood your email service.
Fix
Apply the same rate limit to all sensitive endpoints, plus add a small per-email cooldown (e.g., "you can only request a password reset once every 60 seconds for the same email").
Effort
Half a day.
Important

4.3 Test endpoints and seed data live in production

Effort: Small
Plain English
An admin user can press a button that creates five fake Give-a-Key applications and four fake donations. That button exists in the live system. It is unlikely an admin would press it by accident, but it is the kind of thing that should not be available outside a test environment.
Fix
Wrap the seed endpoint in an if (NODE_ENV !== 'production') check, or delete it.
Effort
1 hour.
Important

4.4 Children's first names & interests are sent to an AI on every match

Effort: Medium
Plain English
When the "Run Matching" button is pressed, the names, ages, interests, and home states of every unmatched child are sent to a third-party AI (Anthropic Claude) to suggest pairings. This is documented and works well, but the data leaving your building is not redacted — it leaves with real first names attached.
Why it matters
For a children's product, the bar for data sharing is higher (COPPA, state child privacy laws). At minimum the families should know this happens; ideally the data sent to the AI is anonymised first.
Fix
Replace first names with internal codes ("Child A", "Child B", …) before sending to the AI, and translate back on the way home. Also confirm Anthropic's data retention setting is set to "do not train on submitted data".
Effort
1 day plus a privacy-policy review.
Important

4.5 The "Health" display says matched children are at risk

Effort: Small
Plain English
The dashboard's "At risk" counter is overcounting. Children who are already happily matched are still flagged red because a hidden "days waiting for a match" clock keeps ticking after the match was made. This is purely a display bug, not a data bug — the matches themselves are fine. (See Section 6 for the visual proof.)
Fix
When a match is approved, stop the clock. Either clear the match_guarantee_start_date field or have the "health" calculation ignore children whose status is "Matched".
Effort
2–4 hours.
Important

4.6 Server may not see real visitor IPs

Effort: Tiny
Plain English
The login rate-limiter (20 tries per 15 minutes) is meant to be per visitor. But because the app sits behind Replit's network, the server may see Replit's address for every visitor instead of the visitor's true address. Result: either every visitor in the world counts as one (so 20 attempts kicks in instantly for everyone), or the limit is effectively bypassed.
Fix
Add one line to the server config: app.set('trust proxy', 1). Then verify the right behaviour by attempting 21 fast logins.
Effort
15 minutes.
Important

4.7 Onboarding links never expire

Effort: Small
Plain English
When a new customer signs up via Shopify, we email them a personalised link that lets them add their child's details without a password. That link has no expiry date — once it has been emailed, it works forever, and lets anyone who has the URL add new children to that family's account.
Fix
Give onboarding links a 30-day expiry (matching most other "magic link" patterns), and rotate the token after a child has been added.
Effort
2–4 hours.

5. Useful Improvements — Next Quarter

None of these are blocking. They are the items that turn a working tool into a polished, professionally-run product.

8. Glossary of Terms

Webhook An automatic message one online service sends to another when something happens (e.g. Shopify telling MailDay "an order was just placed").
HMAC signature A short code added to a webhook message that proves it really came from the claimed sender, the way a wax seal proves a letter wasn't tampered with.
Token A short string of letters and numbers that says "the holder of this string is logged in as X". Like a paper wristband at a concert.
localStorage A small storage area in the browser that any script on the page can read and write. Convenient but not private.
HttpOnly cookie A special cookie that the browser will send to the server automatically, but scripts on the page cannot read. The recommended place to store login keys.
CSP (Content Security Policy) A list of rules the server sends to the browser saying "only run scripts from these places". Blocks most cross-site-scripting attacks.
XSS (Cross-Site Scripting) A bug where attacker-supplied text is rendered as code by the browser. The main way login keys in localStorage get stolen.
Rate limiting Refusing to answer if requests come in too fast from the same place. A speed bump.
Bcrypt hash A one-way scramble of a password. The original cannot be recovered. The standard way to store passwords.
Service-role key A master key for the Supabase database that bypasses all access rules. The server has it; nothing else should.
RLS (Row Level Security) A Supabase feature that locks down individual database rows by user. Currently off in MailDay because the Express server is the only thing allowed to touch the DB.
COPPA A US law about collecting personal information from children under 13. Relevant because MailDay stores child data.
SPA (Single Page Application) A website that loads once and then redraws itself as you click. MailDay is one.
